🤔 ¿Por qué Git es crítico en ML?

En desarrollo de software tradicional Git es útil. En ML es indispensable: los experimentos son no-lineales, los datasets cambian, y los modelos evolucionan constantemente.

💡 El problema sin Git: "¿Cuál versión de train.py generó ese 94% de accuracy que vimos hace 3 semanas?" — Sin control de versiones, esta pregunta no tiene respuesta.

🌿 Branching — Experimentos paralelos

Las ramas son la herramienta clave para experimentación en ML. Cada hipótesis tiene su rama; si funciona, se mergea. Si no, queda como referencia histórica sin ensuciar main.

☁️ Colaboración Remota & Pull Requests

GitHub / GitLab son el hub central donde el equipo converge. Los Pull Requests son el mecanismo de revisión — en ML esto incluye revisar no solo código sino también métricas y experimentos. 

# ── Conectar con remoto ───────────────────────────────
git remote add origin https://github.com/user/proyecto-ml.git
git push -u origin main            # Primer push con tracking

# ── Sincronización diaria ─────────────────────────────
git fetch origin                   # Descarga cambios sin aplicar
git pull origin main               # fetch + merge (o rebase con --rebase)
git pull --rebase origin main      # Mantiene historial lineal

# ── Subir experimento para revisión ───────────────────
git switch -c exp/attention-v2
# ... desarrollas y committeas ...
git push origin exp/attention-v2   # Sube la rama

# ── GitHub CLI (recomendado) ──────────────────────────
gh pr create \
  --title "exp: Attention V2 → accuracy=95.1% (+1%)" \
  --body "## Cambios\n- Multi-head attention con 8 heads\n- Dropout 0.1\n\n## Resultados\n| Métrica | Baseline | V2 |\n|---------|----------|----|\n| Accuracy | 94.2% | 95.1% |\n| F1 | 93.8% | 94.9% |" \
  --reviewer @equipo-ml

gh pr list --state open
gh pr merge 42 --squash --delete-branch
Output 
Creating pull request for exp/attention-v2 into main in user/proyecto-ml
https://github.com/user/proyecto-ml/pull/42
💡 Code Review en ML: Además del código, el PR debe incluir: (1) métricas comparativas, (2) ejemplos de predicciones, (3) análisis de errores, (4) tiempo de inferencia.

🚫 .gitignore & Git LFS

Git no debe almacenar datos masivos ni modelos entrenados — eso explota el repositorio. .gitignore excluye archivos; Git LFS permite versionar archivos grandes con punteros ligeros. 

# ── .gitignore para proyectos ML ──────────────────────
# Python
__pycache__/
*.py[cod]
*.so
.env
.env.*
venv/
.venv/

# Datos (usa DVC o S3 para versionar datos)
data/raw/
data/processed/
*.csv
*.parquet
*.json.gz

# Modelos entrenados grandes
models/*.pkl
models/*.pt
models/*.h5
models/*.onnx
checkpoints/

# Experimentos y logs
mlruns/
wandb/
.neptune/
lightning_logs/
*.log

# Jupyter Notebooks — outputs (usa nbstripout)
.ipynb_checkpoints/

# IDE
.vscode/settings.json
.idea/

# ── Git LFS para archivos grandes indispensables ──────
# Instalar: https://git-lfs.github.com
git lfs install
git lfs track "*.pkl"         # Models pequeños con versionado
git lfs track "data/curated/*.parquet"  # Dataset curado y estable
git add .gitattributes        # lfs config va aquí
git commit -m "chore: configure git-lfs for model artifacts"

# Ver archivos bajo LFS
git lfs ls-files

# ── Verificar .gitignore ──────────────────────────────
git check-ignore -v models/bert-finetuned.pt
# → .gitignore:8:models/*.pt    models/bert-finetuned.pt
⚠️ Si accidentalmente committeas un archivo grande, usa git filter-repo (no filter-branch) para limpiarlo del historial completo antes de hacer push.

📦 DVC — Data Version Control

DVC extiende Git para datos y modelos: los archivos grandes van a S3/GCS/Azure Blob; Git solo guarda punteros (.dvc files). Así tienes reproducibilidad completa sin inflar el repo. 

# Instalación
pip install dvc dvc-s3  # o dvc-gs, dvc-azure según tu cloud

# ── Inicializar DVC en el repo existente ──────────────
git init
dvc init
git add .dvc/
git commit -m "chore: initialize DVC"

# ── Conectar storage remoto ───────────────────────────
dvc remote add -d myremote s3://mi-bucket/dvc-cache
# Para local (pruebas):
dvc remote add -d localremote /tmp/dvc-cache

# ── Agregar datos bajo control DVC ────────────────────
dvc add data/raw/dataset_2024.parquet
# Genera: data/raw/dataset_2024.parquet.dvc
# Agrega automáticamente data/raw/dataset_2024.parquet a .gitignore

git add data/raw/dataset_2024.parquet.dvc data/.gitignore
git commit -m "data: add raw dataset 2024 (12GB)"

dvc push   # Sube datos al remote storage

# ── Reproducir en otra máquina ────────────────────────
git clone https://github.com/user/proyecto-ml.git
cd proyecto-ml
dvc pull   # Descarga los datos del remote

# ── Pipeline reproducible ─────────────────────────────
dvc run -n preprocess \
  -d data/raw/dataset.parquet \
  -d src/preprocess.py \
  -o data/processed/clean.parquet \
  python src/preprocess.py

dvc repro         # Re-ejecuta solo lo que cambió
dvc dag           # Visualiza el pipeline
dvc dag 
+----------------------+
| data/raw/dataset.dvc |
+----------------------+
          *
          *
    +------------+
    | preprocess |
    +------------+
          *
     +-------+
     | train |
     +-------+
💡 DVC vs Git LFS: Git LFS versiona archivos individualmente en Git. DVC versiona pipelines completos (datos + código + modelos) con caché compartida y reproducibilidad de experimentos.
